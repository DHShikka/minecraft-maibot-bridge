# 动作与工具参考

这份文档是**双层**的：

- 上表是**线协议层**的 `action` `params`（模组直接执行的东西）；
- 每个动作对应的 **LLM 工具**（麦麦实际调用的 `mc_*`）也一并列出。

所有坐标都使用 **方块坐标（整数）**，与游戏里 F3 显示的一致。所有长任务都有超时，超时后会带着原因失败，不会静默卡住。

## 观察类

### `get_state` → 工具 `mc_state`

拿一份完整状态快照。**行动前最该先调用的东西。**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| — | | | 无参数 |

返回：完整的 `state` 载荷（见 [PROTOCOL.md](PROTOCOL.md#33-state)）。工具层还会把它渲染成一段给 LLM 读的自然语言摘要。

### `scan_blocks` → 工具 `mc_scan_blocks`

在角色附近搜索方块。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `block` | string | 必填 | 方块名（`iron_ore`、`minecraft:diamond_ore`）或标签（`#minecraft:logs`、`#minecraft:flowers`） |
| `radius` | int | 16 | 水平搜索半径，1–64 |
| `yRadius` | int | = radius | 垂直搜索半径，1–128 |
| `limit` | int | 20 | 最多返回几个，1–200 |
| `sortBy` | string | `distance` | `distance` 或 `y`（从高到低） |

返回：

```json
{
  "query": "iron_ore", "radius": 24, "totalFound": 12, "returned": 12,
  "blocks": [
    {"pos": {"x": 30, "y": 42, "z": -11}, "block": "minecraft:iron_ore",
     "name": "铁矿石", "distance": 21.4, "destroySpeed": 3.0}
  ]
}
```

> 只能扫到**已经加载的区块**（玩家附近）。找不到东西时返回带 `hint` 的说明，建议扩大半径或先移动。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message` | string | 是 | 聊天内容，最长 256 字符，换行会被替换成空格 |

### `command` → 工具 `mc_command`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `command` | string | 是 | 指令内容，带不带前导 `/` 都行 |

- 只允许一条指令（换行会被服务端拒绝）。
- 会先过模组的 `commandBlacklist`（默认禁止 `op`/`deop`/`ban`/`kick`/`stop`/`whitelist` 等）。
- 权限取决于角色自身，没有 OP 就会失败——游戏聊天栏会显示失败原因，但**插件侧看不到**（原版不会把指令反馈单独上报，除非它以系统聊天形式出现）。

## 移动类

### `move_to` → 工具 `mc_move_to`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int | 必填 | 目标方块坐标 |
| `range` | int | 1 | 到达判定半径（水平，格） |
| `speedFactor` | number | 1.0 | 0.2–1.0，用于「悄悄靠近」 |
| `allowSprint` | bool | true | 是否允许疾跑 |

返回：

```json
{"pos": {...}, "blockPos": {...}, "targetBlock": "(100, 64, -200)", "pathLength": 34}
```

**内部机制**（已按 Baritone 的思路重写，详见 [`BARITONE.md`](BARITONE.md)）：

寻路把路径表示成一串**移动**（movement），每一步都是一个多 tick 动作，
自己知道代价、也知道该怎么执行：

| 走法 | 说明 |
|---|---|
| 直走 / 斜走 | 同层四向与对角平移（对角不切角） |
| 上台阶 / 下台阶 | 1 格高差 |
| 下落 | 走出边缘往下掉，最多 4 格 |
| **跳过缺口** | 跨越 1–4 格宽的沟（4 格需要疾跑） |
| **向下挖** | 挖穿脚下 1–4 格并落到实地上（下矿道、钻地面） |
| **垫脚上** | 往脚下放方块跳上去（翻 1–2 格高的墙；需要背包里有方块） |
| **挖穿直走** | 挡路的方块直接挖开继续走（受模组 `allowBreakBlocks` 控制） |

代价统一换算成 **tick**，所以取舍会贴近真人直觉：挖穿一格石头约 15 tick ≈ 走 5 格路，
绕路在 5 格以内就不挖，要绕 20 格就直接挖过去。

执行期每 tick 检查「玩家还在不在这一步的合法位置上」，跑出去就**回退一步重跑**
（回退预算 = max(6, 路径长度/2)），预算耗尽才重新规划。

**不能穿过**：未加载区块（客户端读到的是空气，必须整列拦住）、岩浆/火/仙人掌等危险方块、
挖不动的方块（基岩）。

**典型失败原因**：目标被基岩完全封死、垂直落差超过 4 格且无法挖通、需要垫方块但背包里没有。
失败信息会说明「最后停在哪、为什么」，不会再只说一句「找不到路径」。

## 挖掘类

### `mine` → 工具 `mc_mine`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int | 是 | 要挖掉的方块坐标 |
| `requireCorrectTool` | bool | 否 | 手上工具不对时报错而不是硬挖 |

流程：寻路走到够得着的位置 → 视线对准 → `startDestroyBlock` / `continueDestroyBlock` 持续挖 → 验证方块确实变了才算成功。

- 够不到时会自动找「能站、且能打到目标」的落脚点。
- 挖不掉的方块（基岩、传送门框架）会明确报错。
- 超过 60 秒还没破坏会失败，并提示「工具不对，挖掘速度极慢」。

---

### `mine_blocks` → 工具 `mc_mine_blocks`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `block` | string | 必填 | 方块 ID 或标签，例如 `stone`、`#minecraft:logs` |
| `count` | int | 1 | 要挖几个 |
| `radius` | int | 32 | 搜索半径 |

**挖够 `count` 个就停**：扫一次会把附近匹配的方块排进候选，但每挖掉一个都会重新判断够没够。
（真机自检里抓到过反例：`count=3` 实际挖了 64 个，因为「够没够」的判断写在取候选之后。
在游戏里的表现就是「一直挖个不停」，现在修好了。）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `block` | string | 必填 | 方块名或 `#标签` |
| `count` | int | 1 | 要挖几个 |
| `radius` | int | 32 | 搜索半径，2–64 |

先扫描匹配方块按距离排序，然后逐个挖。够不到的会被跳过并记录，不会让整个任务失败。

```json
{"minedCount": 8, "mined": [{"pos": {...}, "block": "minecraft:iron_ore", "dropped": true}], "skipped": 1}
```

`dropped` 表示手上工具是否正确（不正确的话方块会碎但**不掉落物品**）。

### `dig_shaft`（脚本里叫 `dig_shaft`，暂无单独工具）

**阶梯矿道**：从一个点开始，一层一层斜着往下挖，挖穿泥土层到石头层，一路把遇到的矿石记下来。
「够不到铁矿」这件事的入口 —— 地表常常一块铁矿都扫不到，得先下去。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `depth` | int | 20 | 往下挖几层 |
| `x` `y` `z` | int 或 string | — | 可选起点，支持 `~` 相对坐标 |

细节：

- 只挖**能站得住**的落脚点：落点下面没有支撑就不挖，避免挖出个自己爬不上来的深坑。
- 落差超过 3 格会停下来（`MAX_FREE_FALL`）——摔下去掉血比多挖两层亏。
- `dug` **只在确认人真的下去了**才 +1。真机自检抓到过反例：报告「挖了 20 层」，
  而玩家一步没动，因为计数写在「开始移动」而不是「移动完成」。

```json
{"dug": 20, "requestedDepth": 20, "pos": {"x": 120, "y": -12, "z": -300},
 "found": [{"pos": {...}, "block": "minecraft:iron_ore"}], "stoppedBecause": ""}
```

## 放置与交互类

### `place` → 工具 `mc_place`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int 或 string | 是 | 要放置方块的目标坐标（必须可替换：空气/水/草） |
| `item` | string | 否 | 放置前先切换到这个物品（模糊匹配） |
| `slot` | int | 否 | 或者直接指定快捷栏槽位 0–8 |
| `face` | string | 否 | 优先点哪一面：`up`/`down`/`north`/`south`/`east`/`west` |

坐标支持 Minecraft 自己的**相对写法**：`"~"` 是玩家脚下那一格，`"~-1"` 是往下一格，
`"~2"` 是往上两格；三个分量可以混着写（`{"x": 5, "y": "~-1", "z": "~"}`）。
相对坐标由模组在开始执行时按玩家位置解析 —— 这一点对**脚本**是必需的：
脚本是提前写好的，写的时候不可能知道玩家会站在哪。

流程：找相邻实体方块的表面 → 走过去 → 看向那个面 → `useItemOn`（和真人右键完全一致）。

- 目标位置被占住会直接报错并建议先 `mine`。
- 附近没有可点击的面会报错（不能凭空放空中）。
- 点击已发出但目标位置仍是空的，会返回 `placed:false` 加一句提示（服务器拒绝、距离过远、权限不足）。

### `bucket` → 工具 `mc_bucket`

装液体 / 倒液体。**做黑曜石（也就是搭地狱门）绕不开它**：黑曜石 = 岩浆源 + 水。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `mode` | string | 必填 | `fill`（装液体）或 `empty`（倒液体） |
| `fluid` | string | `water` | `fill` 时装哪种：`water` / `lava` |
| `x` `y` `z` | int 或 string | | `mode=empty` 必填，液体倒在哪一格；支持 `~` 相对坐标 |
| `radius` | int | 24 | `fill` 时找液体的搜索半径，4–64 |

阶段是 `FIND → APPROACH → USE → VERIFY`，里面有三件手工做很烦的事：

1. **只认源头**：只会点 `isSource()` 的液体方块 —— 点流动的岩浆什么都不会发生。
   找不到源头时会明说「流动的液体装不起来」。
2. **倒的位置算好了**：流体落在**点击面的相邻格**，所以想倒在 `(x,y,z)` 就得点
   `(x,y-1,z)` 的上面。这一步模组自己算，调用方只给最终落点。
3. **自动换桶**：手上是空桶还是水桶/岩浆桶，它自己切。

返回：

```json
{"mode": "fill", "fluid": "water", "got": "minecraft:water_bucket",
 "buckets": 1, "source": {"x": 9, "y": -61, "z": -6},
 "content": "装到了水（手上 minecraft:water_bucket ×1，背包里一共 1 桶）"}
```

> **两个真机自检里踩出来的坑（都在代码注释里记着）**
>
> - **装液体走 `useItem`，不是 `useItemOn`。** 流体方块没有碰撞箱，客户端射线打不到它；
>   原版「对着水右键」实际走的是「使用物品」那条路（`ServerboundUseItemPacket`）。
> - **倒液体也走 `useItem`。** 这点反直觉：`BucketItem` **没有**重写 `useOn`，
>   所以「对方块使用」走到 `Item.useOn` 就返回 `PASS`，一滴都倒不出来。
>   原版右键方块能倒出液体，是因为 `startUseItem` 在 `useItemOn` 没消费之后**又回退到 `useItem`**。
>   自检里倒水/倒岩浆各试 6 次全空、桶还原封不动拿在手上，就是少了这个回退。
> - **判定成功不能只看手。** 手里拿着一叠空桶时（比如 `give bucket 3`），原版
>   `ItemUtils.createFilledResult` 会把装好的桶塞进背包**别的格子**，手上那叠只是少一个，
>   而且返回的还是同一个 `ItemStack` 对象 —— `MultiPlayerGameMode.useItem` 见
>   `itemstack1 == itemstack` 就完全不碰手持栏。所以判据是
>   「手上是装好的桶 **或** 背包里目标液体桶的总数变多了」。

搭地狱门的典型用法：

```json
{"steps": [
  {"action": "bucket", "params": {"mode": "fill", "fluid": "lava"}},
  {"action": "bucket", "params": {"mode": "empty", "x": 10, "y": 64, "z": -3}},
  {"action": "bucket", "params": {"mode": "fill", "fluid": "water"}},
  {"action": "bucket", "params": {"mode": "empty", "x": 10, "y": 65, "z": -3}}
]}
```

#### 浇筑黑曜石：水必须**流进**岩浆源

这一条是真机上反复试出来的，写下来免得再踩：

| 情况 | 结果 |
|---|---|
| 水**流进**一个岩浆**源** | ✅ **黑曜石** |
| 水碰到**流动的**岩浆（岩浆已经摊开了） | ❌ 圆石 |
| 岩浆流进水里 | ❌ 圆石（或者石头） |

所以「倒一桶岩浆再倒一桶水」这件事，有两个必须遵守的前提：

1. **岩浆得待在坑里，保持是「源」。** 倒在开阔平地上它会立刻摊开两三格，
   等水倒下去时碰到的是**流动岩浆** —— 出来的是圆石。真机实测就是这样：
   平地上倒了一桶岩浆，十秒后倒水，得到的是 `(73,28,184)` 的圆石，不是黑曜石。
   **正确做法**：先挖一格深的坑，把岩浆倒进坑里（四周被方块夹住，流不出去），
   再倒水。
2. **倒水不能瞄着岩浆格。** 倒液体时模组点的是「目标格**下面那一格**」的顶面，
   而射线用的是 `Fluid.NONE` —— 它会**穿过**液体，永远打不到岩浆方块本身。
   所以水的落点必须选一个**下面有实心方块**的格子，摆在岩浆旁边，
   让水自己流进坑里。直接写「倒在岩浆正上方」是做不到的，模组会明确报
   「周围没有既站得住、又看得见它的格子」。

推荐的三步（每格黑曜石）：

```
mine   (x, y, z)          ← 挖一个 1 格深的坑
bucket mode=empty fluid=lava  倒进坑里 (x, y, z)     ← 下面有坑底，射线打得到
bucket mode=empty fluid=water 倒在坑旁边 (x+1, y, z) ← 地面是实心的，水会流进坑里
```

另外两条经验：

- **岩浆源舀一桶就少一格**（`pickupBlock` 会把源方块挖掉）。想凑 10 格黑曜石，
  就得有 10 个岩浆源 —— 找真正的岩浆湖，别指望一个小坑。
- **装液体时射线必须真能看见液面**。液体在坑里、被方块挡着时，站在三四格外的射线
  会先打在坑沿上（真机原话：「视线探针：打到 (1,-61,-8) 的 up（grass_block）」），
  模组现在会先检查这一点，够不着就直接说清楚，不再白点六次。

## 合成类

### `recipes` → 工具 `mc_recipes`

只读查询，**不改动世界**。给出能产出指定物品的所有合成配方。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `item` | string | 必填 | 要查询的物品名（原版 ID 或中文名，支持模糊匹配） |

每条配方给出：产物与数量、需要的工作台尺寸（2x2 还是 3x3）、配方是否已解锁、材料清单、以及**当前背包里的材料够不够**。

### `craft` → 工具 `mc_craft`

真正动手合成。模组会自动完成整条链路。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `item` | string | 必填 | 要合成的物品名（支持模糊匹配） |
| `count` | int | 1 | 想要几个成品 |
| `maxCrafts` | int | 64 | 最多合成几次（安全阀） |

内部流程：

1. **找配方** —— 在 `RecipeManager` 里找出所有能产出该物品的配方。有多个候选时（比如木板可以由各种原木做），优先选**材料够用的**，其次选**2x2 就能做的**（不用找工作台）。
2. **查材料** —— 贪心核对背包是否凑得出材料。缺什么会明确列出来，例如「还缺：stick、cobblestone」。
3. **查解锁** —— 配方书里没有这个配方就直接说明原因（配方书路径的前提）。
4. **选容器** —— 2x2 用背包自带合成格（`InventoryMenu`）；3x3 去找附近 8 格内的工作台，走过去右键打开。附近没有工作台会明确告诉 AI「先 `mc_craft crafting_table` → `mc_place` → 再来」。
5. **合成循环** —— 反复「让服务器摆材料 → 隔几 tick 检查结果槽 → shift 点击结果收进背包」，直到做出目标数量或材料耗尽。
6. **验证** —— 对比合成前后的背包数量，如实报告实际拿到多少。

返回：

```json
{
  "item": "oak_planks", "crafted": 4, "countBefore": 0, "countAfter": 16, "received": 16,
  "recipe": "minecraft:oak_planks", "outputPerCraft": 4,
  "recipeDetail": {"needsTable": false, "unlocked": true, "ingredients": ["#minecraft:oak_logs"]}
}
```

#### 为什么走「配方书」而不是手动摆格子

客户端合成有两条路：

| | 配方书 | 手动摆格子 |
|---|---|---|
| 做法 | 发一条 `ServerboundPlaceRecipePacket`，**服务端**把材料摆进格子 | 用 `handleInventoryMouseClick` 一个个点进格子 |
| 谁负责正确性 | 服务端（权威） | 客户端自己算形状、映射格子、控制每次点几个 |
| 出错后果 | 「什么都没发生」，可检测、可解释 | 一旦某次点击与服务器状态不一致就**静默失步**，后续操作全部错位 |

选了前者。失败模式可控，而且能给出「材料不够 / 配方没解锁 / 附近没工作台」这类能直接照做的原因。

#### 已知限制

- 需要 3x3 的配方要求**附近已有工作台**。模组不会自己去造、自己去放 —— 这两步本身就是自然动作，交给 AI 自己规划更清楚（而且它用 `mc_craft crafting_table` + `mc_place` 就能做）。
- 配方必须**已解锁**（游戏里捡到材料时通常会自动解锁）。这是原版机制，不是限制。
- 特殊配方（盔甲染色、旗帜复制等 `isSpecial()`）不能自动完成，会明确报错。
- 烧矿/烧食物是另一个动作：`smelt`（见下）。工作台不管熔炼。

### `smelt` → 工具 `mc_smelt`

把东西**烧出来**：生铁→铁锭、沙子→玻璃、生肉→熟肉。挖到铁矿只是第一步，
没有这一步就没有铁镐、没有桶（也就没有黑曜石和地狱门）。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `item` | string | 必填 | 要**烧出什么**，例如 `iron_ingot`、`glass` |
| `count` | int | 1 | 要几个（下限 1） |
| `radius` | int | 8 | 找熔炉的搜索半径 |

流程：找最近的熔炉 → 走过去 → 开界面 → 放原料和燃料 → 等烧完 → 把成品收进背包。
原料和燃料都是**按配方查出来的**（`RecipeType.SMELTING`），燃料用
`ForgeHooks.getBurnTime` 验证过确实能烧，不会把圆石当燃料烧掉。

> **为什么是「精确点格子」而不是 Shift 快速移动**
>
> 最早用 Shift 点击（`QUICK_MOVE`）让服务端自己分配，结果烧出来的是**木炭**不是铁锭：
> 原木既是可烧的东西又是燃料，原版会把 Shift 点进来的原木放进**原料格**。
> 现在改成精确的点选序列（PICKUP → 放进目标格 → 余量还回去），
> 「哪个格子放什么」由我们说了算。

返回：

```json
{"item": "minecraft:iron_ingot", "received": 3, "input": "raw_iron", "fuel": "coal",
 "countBefore": 0, "countAfter": 3, "smeltedAt": {"x": 120, "y": 64, "z": -300}}
```

缺原料、缺燃料、附近没熔炉、烧着烧着熔炉被拿走，都会给出明确原因
（而不是干等到超时）。

### `script` → 工具 `mc_script`

**任务组**：一次下发一整段流程，模组本地连续执行，只在结束时回传一次聚合结果。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `steps` | array | 必填 | 步骤数组，见 [SCRIPT.md](SCRIPT.md) |
| `name` | string | — | 人类可读的名字 |
| `maxSteps` | int | 200 | 最多执行多少个动作 |
| `maxDurationMs` | int | 600000 | 最长执行时间 |

和上面每个动作都不一样：它的 `params` 不是「做什么」，而是**一串要做的事**。支持
动作、`repeat`、`while`、`if`/`else`、`waitUntil` 五种节点和一套条件表达式。

存在的理由只有一个字：**快**。原来「AI 想一步 → 下发 → 等结果 → 再想」，
瓶颈是每一步都要 AI 重新思考一轮；任务组让 AI 一次把整段流程说完。
做一把石剑从 9 轮思考变成 1 轮。

权限上它不做例外：脚本里每个动作都由 `ActionExecutor.createTask` 创建，
走的是和单独下发**完全相同**的权限开关、参数校验与每秒动作数限速
（被限速时脚本挂起等下一个时间窗，而不是失败）。
细节、语法、例子和**预设**（`preset="wooden_pickaxe"` 这种）见 **[SCRIPT.md](SCRIPT.md)**。

## 战斗类

### `attack` → 工具 `mc_attack`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `target` | string | 必填 | 玩家名 / 实体名 / uuid / `nearest_hostile` / `nearest` |
| `count` | int | 0 | 最多打几下；`0` 表示打到死（上限 200） |
| `durationMs` | long | 30000 | 最长打多久 |

细节：

- **等攻击冷却**（`getAttackStrengthScale(0.5f) > 0.9`）再出手，否则只有半伤。
- 够不到会自动走过去（判定距离 2.9 格）。
- 目标死亡、消失、变成创造模式玩家都会立刻结束并说明原因。
- 追了 20 秒还够不到（一次都没打中）会放弃并说明目标可能移动太快或在墙后。
- **有盾牌就举盾**：副手有盾（或背包里有，模组会自动换到副手）时，敌人靠近就举起来格挡。
- **目标在天上就换弓**：会飞的（幻翼/烈焰人/恶鬼）或者高出一大截的，近战走过去也是白走 ——
  自动换弓、按距离算**下坠提前量**、拉满一秒再放箭。没有弓/箭会直接说明要准备什么，
  而不是傻追到超时。

### 被打就还手（不用下发动作）

这是**模组自己的行为**，配置在 `[combat]`：

| 配置 | 默认 | 行为 |
|---|---|---|
| `autoFight` | true | 被生物打了 → **立刻中断手上的活**（挖矿/放置/走路），转身打回去 |
| `autoAttackHostiles` | true | **主动出击**：附近有敌对生物就上去打，不等它先动手 |
| `autoAttackRadius` | 12 | 主动出击的警戒半径 |
| `autoAttackCooldownMs` | 4000 | 两轮主动出击之间至少隔多久 |
| `autoAttackMaxKills` | 4 | 一轮最多清掉几个 |
| `targetRequireLineOfSight` | true | **选目标要视线通畅**：被方块挡住的不算目标（不隔墙砍） |
| `targetSkipInvisible` | true | 隐身的目标跳过 |
| `targetBlacklist` | 见下 | **永远不主动攻击**的实体列表 |
| `useShield` | true | 有盾就换到副手，敌人靠近就举盾 |
| `useBow` | true | 目标在天上/会飞时自动改用弓 |
| `autoReload` | true | **弹匣清空自动换弹**（托管 + 闲着 + 背包有同口径子弹时） |
| `autoFightCooldownMs` | 1500 | 两次自动反击的最短间隔（被连打时不反复重开任务） |

`targetBlacklist` 默认拉黑：村民、流浪商人、铁傀儡、雪傀儡、盔甲架、蝙蝠、
狼、猫、鹦鹉、悦灵、美西螈、物品展示框、画。
**理由**：AI 手里有剑的时候去打村民是纯粹的破坏行为，而且这类目标对「活下去」毫无帮助。
想让它打谁，把谁从这个列表里删掉即可。

> 选目标的三条筛选（视线通畅 / 跳过隐身 / 黑名单）**参考了 [10089YMGC/AutoAim](https://github.com/10089YMGC/AutoAim)**：
> 那个模组的自瞄在锁目标之前也是先过一遍筛选 —— 尤其是**从眼睛到目标眼睛投一条射线、
> 被方块挡住就换目标**这一条。我们原来只看距离，会出现「隔着墙对着墙砍」。
> 远程武器的瞄准点也照它改成**瞄眼睛**（`getEyePosition()`），比瞄身体中心命中率高。

### 手里是远程武器，自动战斗就用远程打

**手上拿什么，自动战斗就用什么** —— 拿着枪还上去抡拳头，等于把枪白带了。
这条对「被打就还手」和「主动出击」都生效，判断只看**手上那把**（不去背包里翻别的武器，
不然会出现「我只想挖矿，它却掏出枪乱打」）：

| 手上的东西 | 自动战斗怎么做 |
|---|---|
| 枪，弹匣里有弹 | 直接**开枪**（走模组接口，见下面「远程武器」一节），一个点射约 14 tick |
| 枪，弹匣空了但背包有匹配口径的子弹 | **先换弹**，换完下一轮接着打 |
| 枪，弹匣空、背包也没子弹 | 退回近战（动作结果里会说明为什么） |
| 弓 / 弩（有箭）、三叉戟 | 用远程 |
| 空手 / 近战武器 | 近战（空手时会先换一把武器） |

真机实测：拿 AK 时日志是 `自动反击：史莱姆（打断当前动作，用枪打）`；
弹匣打空、背包也补不上之后，同一条日志变成 `（打断当前动作，近战）`。

### 弹匣清空自动换弹（`[combat] autoReload`）

打完一梭子之后手上就是一把空枪 —— 下一次开火只会回一句「没有子弹了」，
中间白白浪费一轮往返。所以**弹匣一空就自己补上**：

```
shoot → {"shots": 30, "magazine": 0, "warning": "弹匣打空了，背包里还有 70 发备弹 —— 会自动换弹。"}
（玩家没下任何指令）
状态 → HasBulletInBarrel=1, GunCurrentAmmoCount=29
```

触发条件四条，缺一不可：**手上是枪** + **弹匣空（膛里也没压着）** +
**背包里有同口径子弹** + **自己正闲着**；另外**只在 AI 托管时**生效 ——
你自己玩的时候绝不抢你的 R 键。

战斗过程中不走这一条：那时由战斗逻辑按手里的武器和距离自己决定该射、该换还是该抡
（贴脸时站着换弹会被打死，见上面那张表）。

> 真机注意：`shots: 30` 说明 AK 一个弹匣正好 30 发，
> `taczResult` 最后停在 `NO_AMMO` —— 这不是失败，是「打到空了」的正常收尾。

> **为什么必须「打断」**：真机上最常见的挨打场景是**挖矿挖到一半被僵尸站背后打**，
> 不打断的话它会一直挖到你死。反击会插到队首，打完 20 秒或目标死亡就结束。
> 真机实测日志：`自动反击：僵尸（打断当前动作，用枪打）`，被取消的那个动作失败原因是
> `被 僵尸 攻击，先还手`。

> **主动出击的两条自我约束**（都是真机撞出来的）：
>
> - **贴脸（≤6 格）不管手上在干什么都先打。** 一开始的规则是「手上有活就不打扰」，
>   结果真机上一次都没触发过 —— 因为 AI 几乎总有任务在跑，连一个 `wait` 都算「有活」。
>   现在贴脸会打断：`有 僵尸 贴到 6 格，先打它`。
> - **只在 AI 托管时生效**，你自己玩的时候不会被抢手柄；Baritone 在干活时也不插手
>   （它可能正在挖矿，开战会互相打架），除非敌人已经贴脸。

### AI 托管（`mc_takeover` / `[takeover]`）

麦麦接手之后，玩家可以**放开鼠标、切出去干别的**，游戏照常跑、AI 照常操作。

| 配置 | 默认 | 作用 |
|---|---|---|
| `autoOnConnect` | true | 麦麦（插件）一连上就自动进托管；断开时自动还原 |
| `releaseMouse` | true | 托管时把鼠标从窗口里放开（不然玩家一碰鼠标就和 AI 抢视角） |

它解决的其实是**原版单人游戏的两个「人在电脑前」假设**：

1. **窗口失焦就暂停**（`pauseOnLostFocus`）。暂停时集成的服务端不 tick ——
   表现就是「AI 一步都走不动、指令执行了但方块不变」。真机排查这个现象花了很久，
   游戏日志里的原话是 `Saving and pausing game...`。
2. **鼠标被锁在窗口里**，玩家一动就跟 AI 抢视角。

进托管后：AI 的动作走 `InputController`（直接写 `KeyMapping` 状态），**和窗口焦点无关**，
照常生效；玩家点回窗口就能随时接管。状态快照里会带 `takeover.active`，
`mc_state` 会写明「AI 托管中：窗口失焦不会暂停，鼠标已放开」。

### 远程武器：弓 / 弩 / 三叉戟 / 枪械（`mc_shoot`）

**任何远程武器都能用**，模组会看手上（或背包里）有什么自动选一把：

| 类型 | 怎么开火 |
|---|---|
| 弓 | `useItem` 拉满约 1 秒再松开 |
| 弩 | 同上，但上弦更慢（单独给了时长） |
| 三叉戟 | 蓄力约 10 tick 后投掷 |
| 枪（TaCZ 这类） | 优先**直接调模组的开枪接口**；拿不到才退回「按住开火键」——原因见下 |

**枪为什么要绕开按键**（这段是反编译 TaCZ 的字节码才弄明白的，踩了两个坑）：

1. **开火不是按键事件，是每 tick 轮询**。TaCZ 的 `ShootKey.autoShoot` 在
   `TickEvent.ClientTickEvent` 里读它自己的 `SHOOT_KEY.isDown()`，
   **完全没有 `InputEvent` 监听** —— 所以「发个按键事件」对它无效，
   连改原版攻击键也没用（`SHOOT_KEY` 是模组另外注册的一个 `KeyMapping`）。
2. **它有一道输入闸门，和 AI 托管直接冲突**。`InputExtraCheck.isInGame()` 要求
   鼠标被锁在窗口里、而且窗口在前台：

   ```java
   if (mc.overlay != null) return false;
   if (mc.screen  != null) return false;
   if (!mc.mouseHandler.isMouseGrabbed()) return false;   // ← 托管时鼠标是放开的
   return mc.isWindowActive();
   ```

   而「AI 托管」这个功能本身就要 `releaseMouse()`（玩家才能切出去），
   于是按键路线**永远过不了这道检查**：真机上弹匣压满 29 发、键也按对了
   （`key.tacz.shoot.desc`），`ammoUsed` 一直是 0。

所以现在走它自己的接口（`IClientPlayerGunOperator.fromLocalPlayer(player).shoot()`
/ `.reload()`），这正是 TaCZ 开火键按下后调的东西，只是跳过了输入闸门。
**用反射拿**，没装 TaCZ 时全部返回 null 并自动退回按键路线，不构成编译期依赖。
开火结果里会写明这次走的是哪条路（`via: tacz-api` / `via: key(...)`）和模组回的状态。

模组回的状态也会照实转述，例如 `IS_RELOADING`（正在换弹）、`NOT_DRAW`（还没掏枪，
会自动补一个掏枪动作）、`NEED_BOLT`（要先拉栓）、`COOL_DOWN`（射速冷却）。
这几种**临时**状态不算失败：动作会多等最多 2 秒再收工，
所以「刚换完弹立刻开火」不会空手而归（真机第一次就是栽在这上面）。

**「记得带子弹」是硬规则，不是提示**：开火之前**先数弹药**，一发都没有时**不会扣扳机**，
而是明确回一句「没有箭/子弹了，先去补，或者改用近战」——
空放一枪在游戏里表现为「什么都没发生」，AI 会以为是自己瞄歪了，然后一直瞄。
每次开火的结果里都带剩余弹药，剩 8 发以下会提醒补；状态快照里的 `ranged` 字段随时能查。

**「响没响」以弹药真的少了为准**，不是以「我扣了扳机」为准：`fired` 是算出来的
（`ammoUsed > 0`），枪没响时会附上模组回的状态和这次用的键，便于排查。

各家的弹药怎么数：

- 弓/弩：背包里的箭（普通/光灵/药箭都算）；弩还认烟花火箭；
- 枪：**弹匣**（TaCZ 的 `GunCurrentAmmoCount` + 膛内 `HasBulletInBarrel`，标签名是从字节码里挖出来的）
  **加上**背包里匹配口径的子弹物品（按命名空间 + `ammo`/`bullet` 找）；
- 三叉戟：它本身就是武器，扔出去会回来，不消耗。

动作参数：`reload`（换弹，**只对枪有意义**，弓/弩/三叉戟直接 `shoot`）、
`shoot` + 可选 `target`（先瞄准再开火，瞄的是 `getEyePosition()` —— 参考 AutoAim）、
`ticks`（开火持续多少 tick，默认 3；一个点射给 12～20）。

**换弹是「等弹匣真的进弹」才报成功**，不是按下键就报：TaCZ 要播完换弹动画（AK 约 2.5 秒），
所以动作会一直等到 `GunCurrentAmmoCount` 变大，结果里带 `magazineBefore` / `magazine`。
等了 8 秒还没变就老实说没换成，并列出常见原因（口径不匹配 / 弹匣本来就满 / 换弹键不对）。

换弹键同样先走模组接口，拿不到才去找按键（早先反射 `KeyMapping.ALL` 一直失败 ——
运行时字段名是 SRG，反射用的字符串不会被重映射；现在改读公开的 `Options.keyMappings`，
模组的键就都在里面了）。


### 夜视：把亮度强行拉满（`[visual] gamma`）

洞穴里 `lightLevel = 0` 时原版画面是全黑的。模组可以把客户端的**伽马值**强行拉到指定值，
效果就是常说的 fullbright / 夜视：

```toml
[visual]
# 0 = 不动玩家的设置；1.0 = 原版上限；10 以上基本全亮（推荐 10）
gamma = 10.0
```

- 这是**纯客户端显示设置**，不改变服务器上的任何东西，也不影响游戏规则
  （和喝夜视药水不是一回事）。
- 退出游戏时它会写进 `options.txt` —— 也就是说**它会留在你的游戏设置里**，
  不会自己还原。不想要了就把 `gamma` 改回 0（或者把游戏里的「亮度」拖回去）。
- 只在值不一致时才写，不会每 tick 去动设置对象。

返回：

```json
{"hits": 7, "reason": "目标已死亡", "target": "nearest_hostile",
 "initialHealth": 20.0, "killed": true}
```

### `defend` → 工具 `mc_defend`

**抵御**：自己评估局势，清掉附近的敌对生物。和 `attack` 的区别是它**有战术**——
不是「打某一只」，而是「守住这一片」，中途会根据自身情况改主意。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `radius` | int | 16 | 威胁判定半径（3~64） |
| `maxKills` | int | 8 | 最多清掉几个 |
| `retreatHealth` | double | 8 | 血低于这个值先自保 |
| `flee` | bool | false | 只跑不打 |
| `x` `y` `z` | int | — | 可选驻守点；清完威胁会走回去（`y` 省略就用当时的高度） |
| `durationMs` | long | 60000 | 最长抵御多久 |

决策优先级（实现在 `DefenseTactics`，纯逻辑、有单测）：

1. 附近没威胁 → 收工（有驻守点就先走回去）
2. `flee=true` → 只撤
3. 血 ≤ `retreatHealth`：**有吃的先吃**，没吃的才撤
4. 被 3 个以上围住而且血不到一半 → 撤
5. 否则 → 打

打谁也有优先级：**正在打我**的 > **够得着**的 > 近的。
（正在打我却不还手，会一直挨打；去追墙后/头顶的那种，只会被别的怪白打。）

它内部复用 `attack` / `move_to` / `use_item` / `equip` 这些标准动作（走的是同一个
`ActionExecutor.createTask`，所以权限开关一致），不重写战斗细节：

- 手上不是武器 → **先自动换上**剑/三叉戟（其次斧头）；
- 要吃但手上不是食物 → 先换再吃；
- 被围/残血 → 往威胁的**反方向**走 12 格。

返回：

```json
{"kills": 3, "reason": "威胁已清除",
 "healthStart": 20.0, "healthEnd": 20.0, "healthLowest": 20.0,
 "remaining": [],
 "log": ["→ 换上 minecraft:iron_sword", "✓ 换上了 minecraft:iron_sword",
         "→ 打 僵尸（3 格外）", "✓ 打完了 僵尸（击杀以实际倒下的为准）",
         "✓ 僵尸 倒下了（累计 3）"]}
```

> **击杀数怎么算**：以「**看到它倒下**」为准，不是「attack 任务返回成功就 +1」。
> 真机自检里出现过：铁剑的横扫把旁边两只一起带走，三只全倒，而只写「清掉 1 个」——
> 因为那一轮只直接打了其中一只。现在按观察统计，横扫、烧死、摔死的都算得上。

## 控制类

### `look` → 工具 `mc_look_at`

三选一：

| 参数组合 | 行为 |
|---|---|
| `x` `y` `z` | 看向世界坐标（可以是小数） |
| `entity` | 看向实体（玩家名/实体名/uuid） |
| `yaw` / `pitch` | 直接设定角度 |

`pitch` 会被夹到 -90~90。会同时设置 `yRot`、`yHeadRot`、`yBodyRot`，观感与真人一致。

## 模组侧的执行调度规则

1. **即时动作**（`chat` / `command` / `get_state` / `scan_*` / `equip` / `drop` / `use_item` / `look` / `stop` / `cancel` / `task_status`）收到就当 tick 执行，结果立刻回传。
2. **长动作**（移动、挖矿、放置、战斗、跟随、等待…）进队列，每 tick 推进一步，并每 2 秒上报一次 `task_progress`。
3. **同一时间只允许一个「移动类」动作**。新来的移动动作会：
   - 取消正在执行的移动动作（它会收到 `ok=false` + 「已被更新的移动指令取代」）；
   - 清掉队列里还没开始的移动动作；
   - 自己插到队首。
   
   这样 AI 改主意时不用等旧任务跑完。
4. **全局限速**：每秒最多 `maxActionsPerSecond`（默认 20）个动作，超了直接拒绝。
5. **队列上限**：`maxQueuedActions`（默认 32），超了拒绝并提示先 `stop`。
6. **离开世界时**：所有未完成动作立刻以「玩家已离开世界」失败，虚拟按键复位（不会出现「切世界后角色还在被幽灵按键控制」）。

## 给 LLM 的失败信息长什么样

每个失败都尽量写成「原因 + 建议」，例如：

> 连续 80 tick 无法前进，目标可能被完全封死（(120, 40, -300)）。建议先挖开挡路的方块，或换一个目标。

> 找不到可以站在 (120, 40, -300) 旁边的落脚点。这个方块可能被完全包围，或者悬在够不到的地方。

> 挖 (12, 30, 5)（minecraft:ancient_debris）超过 60 秒仍未破坏。手上没有正确的工具，挖掘速度会非常慢；建议先 equip 一把合适的工具，或者换一个目标。

> 跟随「Alex」时反复寻路失败：找不到通往 (…) 的可行路径。建议先走到开阔处…

这样做是刻意的：麦麦看到的是一个能据以决策的句子，而不是一句 `ERROR`。
