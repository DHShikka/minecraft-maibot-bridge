# 动作与工具参考

这份文档是**双层**的：

- 上表是**线协议层**的 `action` `params`（模组直接执行的东西）；
- 每个动作对应的 **LLM 工具**（麦麦实际调用的 `mc_*`）也一并列出。

所有坐标都使用 **方块坐标（整数）**，与游戏里 F3 显示的一致。所有长任务都有超时，超时后会带着原因失败，不会静默卡住。

### `scan_blocks` → 工具 `mc_scan_blocks`

在角色附近搜索方块。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `block` | string | 必填 | 方块名（`iron_ore`、`minecraft:diamond_ore`）或标签（`#minecraft:logs`、`#minecraft:flowers`） |
| `radius` | int | 16 | 水平搜索半径，1–64 |
| `yRadius` | int | = radius | 垂直搜索半径，1–128 |
| `limit` | int | 20 | 最多返回几个，1–200 |
| `sortBy` | string | `distance` | `distance` 或 `y`（从高到低） |

返回：

```json
{
  "query": "iron_ore", "radius": 24, "totalFound": 12, "returned": 12,
  "blocks": [
    {"pos": {"x": 30, "y": 42, "z": -11}, "block": "minecraft:iron_ore",
     "name": "铁矿石", "distance": 21.4, "destroySpeed": 3.0}
  ]
}
```

> 只能扫到**已经加载的区块**（玩家附近）。找不到东西时返回带 `hint` 的说明，建议扩大半径或先移动。

## 通讯类

### `chat` → 工具 `mc_chat`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message` | string | 是 | 聊天内容，最长 256 字符，换行会被替换成空格 |

走的是原版 `ClientPacketListener.sendChat()`，会触发 Forge 的 `ClientChatEvent`，其它模组能看见。受模组配置 `allowChat` 控制。

### `command` → 工具 `mc_command`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `command` | string | 是 | 指令内容，带不带前导 `/` 都行 |

- 只允许一条指令（换行会被服务端拒绝）。
- 会先过模组的 `commandBlacklist`（默认禁止 `op`/`deop`/`ban`/`kick`/`stop`/`whitelist` 等）。
- 权限取决于角色自身，没有 OP 就会失败——游戏聊天栏会显示失败原因，但**插件侧看不到**（原版不会把指令反馈单独上报，除非它以系统聊天形式出现）。

## 移动类

### `move_to` → 工具 `mc_move_to`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int | 必填 | 目标方块坐标 |
| `range` | int | 1 | 到达判定半径（水平，格） |
| `speedFactor` | number | 1.0 | 0.2–1.0，用于「悄悄靠近」 |
| `allowSprint` | bool | true | 是否允许疾跑 |

返回：

```json
{"pos": {...}, "blockPos": {...}, "targetBlock": "(100, 64, -200)", "pathLength": 34}
```

**内部机制**（已按 Baritone 的思路重写，详见 [`BARITONE.md`](BARITONE.md)）：

寻路把路径表示成一串**移动**（movement），每一步都是一个多 tick 动作，
自己知道代价、也知道该怎么执行：

| 走法 | 说明 |
|---|---|
| 直走 / 斜走 | 同层四向与对角平移（对角不切角） |
| 上台阶 / 下台阶 | 1 格高差 |
| 下落 | 走出边缘往下掉，最多 4 格 |
| **跳过缺口** | 跨越 1–4 格宽的沟（4 格需要疾跑） |
| **向下挖** | 挖穿脚下 1–4 格并落到实地上（下矿道、钻地面） |
| **垫脚上** | 往脚下放方块跳上去（翻 1–2 格高的墙；需要背包里有方块） |
| **挖穿直走** | 挡路的方块直接挖开继续走（受模组 `allowBreakBlocks` 控制） |

代价统一换算成 **tick**，所以取舍会贴近真人直觉：挖穿一格石头约 15 tick ≈ 走 5 格路，
绕路在 5 格以内就不挖，要绕 20 格就直接挖过去。

执行期每 tick 检查「玩家还在不在这一步的合法位置上」，跑出去就**回退一步重跑**
（回退预算 = max(6, 路径长度/2)），预算耗尽才重新规划。

**不能穿过**：未加载区块（客户端读到的是空气，必须整列拦住）、岩浆/火/仙人掌等危险方块、
挖不动的方块（基岩）。

**典型失败原因**：目标被基岩完全封死、垂直落差超过 4 格且无法挖通、需要垫方块但背包里没有。
失败信息会说明「最后停在哪、为什么」，不会再只说一句「找不到路径」。

## 挖掘类

### `mine` → 工具 `mc_mine`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int | 是 | 要挖掉的方块坐标 |
| `requireCorrectTool` | bool | 否 | 手上工具不对时报错而不是硬挖 |

流程：寻路走到够得着的位置 → 视线对准 → `startDestroyBlock` / `continueDestroyBlock` 持续挖 → 验证方块确实变了才算成功。

- 够不到时会自动找「能站、且能打到目标」的落脚点。
- 挖不掉的方块（基岩、传送门框架）会明确报错。
- 超过 60 秒还没破坏会失败，并提示「工具不对，挖掘速度极慢」。

---

### `mine_blocks` → 工具 `mc_mine_blocks`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `block` | string | 必填 | 方块 ID 或标签，例如 `stone`、`#minecraft:logs` |
| `count` | int | 1 | 要挖几个 |
| `radius` | int | 32 | 搜索半径 |

**挖够 `count` 个就停**：扫一次会把附近匹配的方块排进候选，但每挖掉一个都会重新判断够没够。
（真机自检里抓到过反例：`count=3` 实际挖了 64 个，因为「够没够」的判断写在取候选之后。
在游戏里的表现就是「一直挖个不停」，现在修好了。）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `block` | string | 必填 | 方块名或 `#标签` |
| `count` | int | 1 | 要挖几个 |
| `radius` | int | 32 | 搜索半径，2–64 |

先扫描匹配方块按距离排序，然后逐个挖。够不到的会被跳过并记录，不会让整个任务失败。

```json
{"minedCount": 8, "mined": [{"pos": {...}, "block": "minecraft:iron_ore", "dropped": true}], "skipped": 1}
```

`dropped` 表示手上工具是否正确（不正确的话方块会碎但**不掉落物品**）。

## 放置与交互类

### `place` → 工具 `mc_place`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int 或 string | 是 | 要放置方块的目标坐标（必须可替换：空气/水/草） |
| `item` | string | 否 | 放置前先切换到这个物品（模糊匹配） |
| `slot` | int | 否 | 或者直接指定快捷栏槽位 0–8 |
| `face` | string | 否 | 优先点哪一面：`up`/`down`/`north`/`south`/`east`/`west` |

坐标支持 Minecraft 自己的**相对写法**：`"~"` 是玩家脚下那一格，`"~-1"` 是往下一格，
`"~2"` 是往上两格；三个分量可以混着写（`{"x": 5, "y": "~-1", "z": "~"}`）。
相对坐标由模组在开始执行时按玩家位置解析 —— 这一点对**脚本**是必需的：
脚本是提前写好的，写的时候不可能知道玩家会站在哪。

流程：找相邻实体方块的表面 → 走过去 → 看向那个面 → `useItemOn`（和真人右键完全一致）。

- 目标位置被占住会直接报错并建议先 `mine`。
- 附近没有可点击的面会报错（不能凭空放空中）。
- 点击已发出但目标位置仍是空的，会返回 `placed:false` 加一句提示（服务器拒绝、距离过远、权限不足）。

---

### `use_on_block` → 工具 `mc_use_on_block`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `x` `y` `z` | int 或 string | 是 | 要交互的方块坐标（同样支持 `~` 相对坐标） |
| `face` | string | 否 | 从哪一面点 |

用于开箱子、按按钮、用工作台、开门。

## 合成类

### `recipes` → 工具 `mc_recipes`

只读查询，**不改动世界**。给出能产出指定物品的所有合成配方。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `item` | string | 必填 | 要查询的物品名（原版 ID 或中文名，支持模糊匹配） |
| `limit` | int | 10 | 最多返回几条，1–50 |

每条配方给出：产物与数量、需要的工作台尺寸（2x2 还是 3x3）、配方是否已解锁、材料清单、以及**当前背包里的材料够不够**。

```json
{
  "query": "stone_sword",
  "found": 1,
  "recipes": [{
    "recipe": "minecraft:stone_sword",
    "output": "minecraft:stone_sword", "outputName": "石剑", "outputPerCraft": 1,
    "needsTable": true, "unlocked": true,
    "ingredients": ["cobblestone", "stick"],
    "ingredientsReady": false
  }]
}
```

### `craft` → 工具 `mc_craft`

真正动手合成。模组会自动完成整条链路。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `item` | string | 必填 | 要合成的物品名（支持模糊匹配） |
| `count` | int | 1 | 想要几个成品 |
| `maxCrafts` | int | 64 | 最多合成几次（安全阀） |

内部流程：

1. **找配方** —— 在 `RecipeManager` 里找出所有能产出该物品的配方。有多个候选时（比如木板可以由各种原木做），优先选**材料够用的**，其次选**2x2 就能做的**（不用找工作台）。
2. **查材料** —— 贪心核对背包是否凑得出材料。缺什么会明确列出来，例如「还缺：stick、cobblestone」。
3. **查解锁** —— 配方书里没有这个配方就直接说明原因（配方书路径的前提）。
4. **选容器** —— 2x2 用背包自带合成格（`InventoryMenu`）；3x3 去找附近 8 格内的工作台，走过去右键打开。附近没有工作台会明确告诉 AI「先 `mc_craft crafting_table` → `mc_place` → 再来」。
5. **合成循环** —— 反复「让服务器摆材料 → 隔几 tick 检查结果槽 → shift 点击结果收进背包」，直到做出目标数量或材料耗尽。
6. **验证** —— 对比合成前后的背包数量，如实报告实际拿到多少。

返回：

```json
{
  "item": "oak_planks", "crafted": 4, "countBefore": 0, "countAfter": 16, "received": 16,
  "recipe": "minecraft:oak_planks", "outputPerCraft": 4,
  "recipeDetail": {"needsTable": false, "unlocked": true, "ingredients": ["#minecraft:oak_logs"]}
}
```

#### 为什么走「配方书」而不是手动摆格子

客户端合成有两条路：

| | 配方书 | 手动摆格子 |
|---|---|---|
| 做法 | 发一条 `ServerboundPlaceRecipePacket`，**服务端**把材料摆进格子 | 用 `handleInventoryMouseClick` 一个个点进格子 |
| 谁负责正确性 | 服务端（权威） | 客户端自己算形状、映射格子、控制每次点几个 |
| 出错后果 | 「什么都没发生」，可检测、可解释 | 一旦某次点击与服务器状态不一致就**静默失步**，后续操作全部错位 |

选了前者。失败模式可控，而且能给出「材料不够 / 配方没解锁 / 附近没工作台」这类能直接照做的原因。

#### 已知限制

- **熔炼（烧矿、烧食物）还没实现** —— 那需要熔炉 + 燃料 + 等待时间，是另一套逻辑。目前只能合成。
- 需要 3x3 的配方要求**附近已有工作台**。模组不会自己去造、自己去放 —— 这两步本身就是自然动作，交给 AI 自己规划更清楚（而且它用 `mc_craft crafting_table` + `mc_place` 就能做）。
- 配方必须**已解锁**（游戏里捡到材料时通常会自动解锁）。这是原版机制，不是限制。
- 特殊配方（盔甲染色、旗帜复制等 `isSpecial()`）不能自动完成，会明确报错。

### `script` → 工具 `mc_script`

**任务组**：一次下发一整段流程，模组本地连续执行，只在结束时回传一次聚合结果。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `steps` | array | 必填 | 步骤数组，见 [SCRIPT.md](SCRIPT.md) |
| `name` | string | — | 人类可读的名字 |
| `maxSteps` | int | 200 | 最多执行多少个动作 |
| `maxDurationMs` | int | 600000 | 最长执行时间 |

和上面每个动作都不一样：它的 `params` 不是「做什么」，而是**一串要做的事**。支持
动作、`repeat`、`while`、`if`/`else`、`waitUntil` 五种节点和一套条件表达式。

存在的理由只有一个字：**快**。原来「AI 想一步 → 下发 → 等结果 → 再想」，
瓶颈是每一步都要 AI 重新思考一轮；任务组让 AI 一次把整段流程说完。
做一把石剑从 9 轮思考变成 1 轮。

权限上它不做例外：脚本里每个动作都由 `ActionExecutor.createTask` 创建，
走的是和单独下发**完全相同**的权限开关、参数校验与每秒动作数限速
（被限速时脚本挂起等下一个时间窗，而不是失败）。
细节、语法、例子和**预设**（`preset="wooden_pickaxe"` 这种）见 **[SCRIPT.md](SCRIPT.md)**。

## 背包类

### `equip` → 工具 `mc_equip`

三选一：

| 参数组合 | 行为 |
|---|---|
| `slot`: 0–8 | 直接选中快捷栏这一格 |
| `item`: 名字 | 在快捷栏里就选中；在背包里就与当前格**交换** |
| `item` + `offhand`: true | 换到副手（例如盾牌） |
| `item` + `armor`: true | 装备到护甲槽 |

`item` 支持模糊匹配：`pickaxe`、`iron_sword`、`铁镐`（本地化名字也能匹配）。找不到时会返回**当前完整背包**，方便 AI 改主意。

实现走 `handleInventoryMouseClick(..., ClickType.SWAP, ...)`，也就是「模拟真人点背包」，服务端会正常校验同步，不会出现客户端单方面改物品导致回弹。

### `drop` → 工具 `mc_drop`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|

| `slot` | int | — | 或直接指定槽位（0–8 快捷栏，9–35 背包） |
| `count` | int | 0 | 丢几个；`0` 表示整叠 |

走 `ClickType.THROW`。

## 战斗类

### `attack` → 工具 `mc_attack`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `target` | string | 必填 | 玩家名 / 实体名 / uuid / `nearest_hostile` / `nearest` |
| `count` | int | 0 | 最多打几下；`0` 表示打到死（上限 200） |
| `durationMs` | long | 30000 | 最长打多久 |

细节：

- **等攻击冷却**（`getAttackStrengthScale(0.5f) > 0.9`）再出手，否则只有半伤。
- 够不到会自动走过去（判定距离 2.9 格）。
- 目标死亡、消失、变成创造模式玩家都会立刻结束并说明原因。
- 追了 20 秒还够不到（一次都没打中）会放弃并说明目标可能移动太快或在墙后。

返回：

```json
{"hits": 7, "reason": "目标已死亡", "target": "nearest_hostile",
 "initialHealth": 20.0, "killed": true}
```

---

### `defend` → 工具 `mc_defend`

**抵御**：自己评估局势，清掉附近的敌对生物。和 `attack` 的区别是它**有战术**——
不是「打某一只」，而是「守住这一片」，中途会根据自身情况改主意。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `radius` | int | 16 | 威胁判定半径（3~64） |
| `maxKills` | int | 8 | 最多清掉几个 |
| `retreatHealth` | double | 8 | 血低于这个值先自保 |
| `flee` | bool | false | 只跑不打 |
| `x` `y` `z` | int | — | 可选驻守点；清完威胁会走回去（`y` 省略就用当时的高度） |
| `durationMs` | long | 60000 | 最长抵御多久 |

决策优先级（实现在 `DefenseTactics`，纯逻辑、有单测）：

1. 附近没威胁 → 收工（有驻守点就先走回去）
2. `flee=true` → 只撤
3. 血 ≤ `retreatHealth`：**有吃的先吃**，没吃的才撤
4. 被 3 个以上围住而且血不到一半 → 撤
5. 否则 → 打

打谁也有优先级：**正在打我**的 > **够得着**的 > 近的。
（正在打我却不还手，会一直挨打；去追墙后/头顶的那种，只会被别的怪白打。）

它内部复用 `attack` / `move_to` / `use_item` / `equip` 这些标准动作（走的是同一个
`ActionExecutor.createTask`，所以权限开关一致），不重写战斗细节：

- 手上不是武器 → **先自动换上**剑/三叉戟（其次斧头）；
- 要吃但手上不是食物 → 先换再吃；
- 被围/残血 → 往威胁的**反方向**走 12 格。

返回：

```json
{"kills": 3, "reason": "威胁已清除",
 "healthStart": 20.0, "healthEnd": 20.0, "healthLowest": 20.0,
 "remaining": [],
 "log": ["→ 换上 minecraft:iron_sword", "✓ 换上了 minecraft:iron_sword",
         "→ 打 僵尸（3 格外）", "✓ 打完了 僵尸（击杀以实际倒下的为准）",
         "✓ 僵尸 倒下了（累计 3）"]}
```

> **击杀数怎么算**：以「**看到它倒下**」为准，不是「attack 任务返回成功就 +1」。
> 真机自检里出现过：铁剑的横扫把旁边两只一起带走，三只全倒，而只写「清掉 1 个」——
> 因为那一轮只直接打了其中一只。现在按观察统计，横扫、烧死、摔死的都算得上。

三选一：

## 模组侧的执行调度规则

1. **即时动作**（`chat` / `command` / `get_state` / `scan_*` / `equip` / `drop` / `use_item` / `look` / `stop` / `cancel` / `task_status`）收到就当 tick 执行，结果立刻回传。
2. **长动作**（移动、挖矿、放置、战斗、跟随、等待…）进队列，每 tick 推进一步，并每 2 秒上报一次 `task_progress`。
3. **同一时间只允许一个「移动类」动作**。新来的移动动作会：
   - 取消正在执行的移动动作（它会收到 `ok=false` + 「已被更新的移动指令取代」）；
   - 清掉队列里还没开始的移动动作；
   - 自己插到队首。
   
   这样 AI 改主意时不用等旧任务跑完。
4. **全局限速**：每秒最多 `maxActionsPerSecond`（默认 20）个动作，超了直接拒绝。
5. **队列上限**：`maxQueuedActions`（默认 32），超了拒绝并提示先 `stop`。
6. **离开世界时**：所有未完成动作立刻以「玩家已离开世界」失败，虚拟按键复位（不会出现「切世界后角色还在被幽灵按键控制」）。

## 给 LLM 的失败信息长什么样

每个失败都尽量写成「原因 + 建议」，例如：

> 连续 80 tick 无法前进，目标可能被完全封死（(120, 40, -300)）。建议先挖开挡路的方块，或换一个目标。

> 找不到可以站在 (120, 40, -300) 旁边的落脚点。这个方块可能被完全包围，或者悬在够不到的地方。

> 挖 (12, 30, 5)（minecraft:ancient_debris）超过 60 秒仍未破坏。手上没有正确的工具，挖掘速度会非常慢；建议先 equip 一把合适的工具，或者换一个目标。

> 跟随「Alex」时反复寻路失败：找不到通往 (…) 的可行路径。建议先走到开阔处…

这样做是刻意的：麦麦看到的是一个能据以决策的句子，而不是一句 `ERROR`。
